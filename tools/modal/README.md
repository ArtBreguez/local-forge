# Modal pipeline (rented GPU lab)

Everything local-forge ran on [Modal](https://modal.com): model comparison, the REA benchmark, the REA training data, the LoRA, the refusals check and the Hugging Face upload. The host (4 GB GPU) only measures speed and fit; quality is measured here, every model in the same container, same llama.cpp build (pinned by digest), same prompts, temperature 0.

Numbers from Modal (CUDA, llama.cpp b12211) are not directly comparable with the host (Vulkan, b12207): compare models within one environment.

## Setup (once)

```bash
uv tool install modal
modal token set --token-id <id> --token-secret <secret> --profile <name>   # type it yourself, never paste tokens in chat
modal profile activate <name>
# Hugging Face write token, for the gated/private dataset and the model upload:
read -rs HF; modal secret create hf-write HF_TOKEN="$HF"; unset HF
```

Volumes are created on first use: `lf-models` (downloaded GGUFs, checked against SHA-256), `lf-lora` (training output and our own GGUFs).

## REA task generator (`tools/rea-bench`)

Every task is a small C program whose function under question is named `proc`; the answer is computed by the generator from its own parameters (never by a model) and each family ships a harness that proves it. One command regenerates any family, from the repo root (stdlib only):

```bash
python3 tools/rea-bench list                                                  # families and variants
python3 tools/rea-bench gen --family crc --n 60 --seed 1001 --out /tmp/crc    # <id>.c + <id>.json per task; --family a,b,c or all
python3 tools/rea-bench check --family all --n 330 --seed 1001                # compile -O0..-O3/-Os -Wall -Werror (gcc, clang if installed), run the harnesses, check the asked constant is in the compiled code, report duplicates
python3 tools/rea-bench survival --family all --n 120                         # per variant: how often the asked constant is in the code, gcc and clang, every -O level
python3 tools/rea-bench stats --seed 7 --n 3000                               # distinct programs per family and overlap with the held-out list
python3 tools/rea-bench heldout [--write]                                     # verify / regenerate the pinned held-out list
python3 tools/rea-bench chance [--write]                                      # per-variant chance level (the `chance` field)
modal run tools/modal/modal_rea_data.py --stage decompile --family crc --n 60 --seed 1001
```

Without `--family`, `modal_rea_data.py` still generates the original 10 templates; `python3 tools/rea-bench --n 60 --seed 1001 --out D` (the old `gen_rea_tasks.py` command line) means `--family legacy`. The `legacy` output is frozen: a test pins its SHA-256 for seeds 1001 (held-out) and 7. `gen` refuses an `--out` that already holds task files unless `--force`. The fact gate needs gcc and objdump (clang too for `--cc mix|clang`) but looks for them only when a task with facts is drawn: `legacy` runs with no compiler at all, and on a machine without clang `--cc mix` gates the gcc draws, warns once and counts the clang draws it could not check (`--cc gcc` gates everything with gcc alone); `--no-survive` skips the gate.

**Held-out and training stay disjoint, as programs.** The held-out split is seed 1001. `tools/rea-bench/rea_bench/heldout-1001.txt` pins the keys of its first 120 tasks per family (the standard `--family all --n 330` split uses 30; a seed-1001 run above 120 per family is refused, since the list does not cover it). A key is the SHA-256 of the task's C body **without its decoy statements** (every decoy line ends with `// decoy` and is stripped), invented identifiers renamed (v0, v1, ...), and its question, so a renamed copy or the same program under other decoys counts as the same task. The decompile stage drops every generated task whose key is in the list or is any later draw the fact gate could have kept in a held-out slot (`--exclude-seed`, default 1001 for any other seed, 0 = off) and prints how many it dropped; `check` reports verbatim repeats inside a seed. Where a family has so few programs that this would drop a large share of training data, the held-out seed draws from reserved parameter values that training seeds never use: seven standard CRC algorithms, the ChaCha/Salsa round counts 10, 14, 18, ... 38, return codes and packet magics that are multiples of 5, and shuffled alphabets only (training also has the standard ones). Measured with the review's `overlap.py` on n=3000 per family at seeds 7 and 8 against the first 120 held-out tasks: **0 training tasks equal a held-out program, decoys stripped, and 0 held-out tasks have a training twin, for every new family** (before: encoding 60%, crc 32%, cipher 28%, antidebug 15% of the held-out tasks had a twin). The frozen `legacy` templates do repeat programs (about 19% of a seed-7 n=3000 set are one of the 120 held-out programs); the exclusion removes them from new training sets.

**Round 8, m11: for the free-string variants, disjoint as answers too.** A held-out task of `strobf/*`, `multi/decode_secret`, `antidebug/env` or the legacy `lcg` has an answer (a plaintext, a secret, a variable name, a multiplier and a round count) that a training task of the same variant can have as well, and the held-out arm would then score a memorised string. At seed 7, `--family all --n 33000`, 439 training tasks had a held-out answer (`antidebug/env` 303 of 500, `strobf` 102 of 3,000, `multi/decode_secret` 26 of 600, `lcg` 8 of 300); `dedupe.ANSWER_DISJOINT` / `heldout_answers` drop them and the decompile stage prints how many (`dropped N generated tasks whose program is not held out but whose ANSWER is ...`), leaving 0 kept tasks of those variants with a held-out answer. Numeric answers from a small space (offsets, sizes, counts, CRC constants, TEA round counts, packet offsets: in 22-100% of a variant's tasks the answer is one that a held-out task of the variant has) are **not** touched: every training set covers them, which is what the `chance` level measures, and dropping them would remove whole variants. The pinned list holds hashes of programs, not answers, so the answer rule uses the held-out draws the generator makes now (`heldout_answers`). The pinned list was regenerated in round 8 (`heldout --write`): 139 of its 1,287 keys changed, because the question of four variants changed (legacy `magic`, CRC `init`, the RC4 and TEA/XTEA hints) or the machines of the two fsm `*_states` variants did (m5).

**Outputs are keyed by seed and family** and never overwritten without `--force`: `decompiled-seed<seed>-<family>.jsonl` (and `/decompiled-seed<seed>-<family>/` on the volume, wiped per run), `sft-<model>-seed<seed>-<family>.jsonl`; a family list joins with `+`, `--family all` is `all`. The sample stage takes the same `--seed` and `--family` as its decompile run. `modal_rea.py` reads every `decompiled-seed1001*.jsonl` for its held-out arm.

Per family the mix is within a few points of the design. One variant is not: `crc/table_poly` keeps 83% gcc (design 60%), because clang folds or vectorises the table-building loop for most parameters and -O levels, so few clang draws keep the polynomial in the code. The other variants the review looked at (`crc/bitwise_poly`, `bounds/char_class`, `structs/init_magic`) are back near the design mix (gcc 64/58/61% against the ungated 59/61/61%; the review measured 68/38/61% after gating) now that a redraw keeps its flags.

Task JSON (new families): `id, kind, question, opt, cc, function, variant, score, accept` and, where needed, `reject`, `cand`, `helpers`, `facts` and `chance`. `cc` is `gcc` or `clang` (60/40 by design, measured below) and `opt` one of -O0..-O3/-Os; `decompile_task` compiles with `task.get('cc','gcc')` and the Modal image has clang. `helpers` names the functions `proc` calls; their pseudocode is appended after `proc`'s in the prompt. `facts` are groups of alternatives (numbers, or strings) that must be in the code compiled at the task's own cc/opt; the generator draws a task again when they are not (`survive.py`; a compiler can fold a loop count into a compare, a polynomial into a vector constant or a table, a character class into one bit mask), and `decompile_task` re-checks them with the Modal image's own compilers. A number counts as present as itself or as the 16/32/64-bit pattern of its negation, never as a truncation of itself (round 2: `0xa001` was "present" because of a `cmp rsi, 1`). A value below 0x20 is in most programs, so for those (loop and round counts, return codes, thresholds, the CRC polynomial and initial value) a group ends with a probe: the gate puts a marker value into the source at the asked place and requires the marker in the compiled code, which a folded constant fails; a CRC polynomial also fails when the object holds a 256-entry table the source does not. ChaCha/Salsa `proc` returns the number of rounds it ran, like TEA's returns its loop count. A task redrawn by the gate keeps its compiler and -O level for the first 8 redraws, so the gate does not skew them. `chance` is the estimated probability that a guess is right (`chance.py`): the larger of the share of tasks with the same question wording that have the same answer (a guesser that samples the answers) and the share of the variant's most common answer (a model that reads the family from the code and guesses the number). Tasks whose answer is computed rather than read (fsm, strobf, multi, loop counts, "which base") carry no `facts`. Where a derived form counts (a range shown as a subtraction and a width, a loop bound one off, `>= N + 1`) the question says so. ARM64 and Windows PE are not generated yet.

Scoring (`tools/rea-bench/rea_bench/scoring.py` and `grammar.py`; an unknown mode raises before any GPU is rented). **Two scorers, one per job** (round 3, m10):

- `score` / `score_any_line` is the **evaluation** scorer (`modal_rea.py`). The original modes `exact`, `any`, `all`, `all_groups` of the legacy templates and the 10 fixed questions are frozen and still score the whole reply by substring, so the 34/60 → 50/60 numbers stay comparable. The modes of the new families score the headline with the grammar below.
- `score_strict` is the **data** scorer (the sample stage and `sft_target`). Every family, legacy included, goes through the grammar; a legacy task is converted first (`strict_task`: its accept strings become grammar groups with the base each number is asked in, an `exact` key an exact string). The conversion keeps no bare hex digits for a decimal key (the hex digits of 39 are `27`, which is another number) and no all-digit text for a hex constant (`30312932` reads as a decimal number), `skip` is a hex value with a `chance` of 0.14 so that agreement applies, and the hash names are those of the template's own algorithm: `fnv`, `fnv-1a`, `fnv1a`, `fnv-32`, `fnv32`; `murmur`, `murmurhash`, `murmur2`, `murmurhash2`, `murmur-ish`; `djb2`, `djb`, `bernstein`, `djb-2` (not `FNV-1`, `MurmurHash3`, `djb2a`: other algorithms). Nothing that is trained on is scored by a substring match: the frozen scorer accepts a content-free reply on 15 of 300 legacy tasks (5%; `check` reports it), the strict one on none (`check` counts that as a problem), and the hex digit `a`..`f` that let any reply with that letter pass is not in the grammar.

The headline rule is a **whitelist**. Rounds 1 to 3 each found a word that was not on a list of hedge words ("at least 40", "≠ 40", "up to 40", `isn´t`), so the scorer no longer looks for bad words: it asks whether the whole headline is an answer and rejects what it cannot parse (`grammar.py`).

- the headline is the first answer line, markdown and backticks removed (a bullet before a digit and a leading `>` are not markdown: `- 40`, `> 40` stay and reject); a bare lead-in line ("Answer:", "Here is the string:") is skipped; if the line holds several sentences the first one is the headline and the rest is justification. What follows the headline must be a sentence of four or more words: a second answer-shaped line, a code block with two values or a list under a lead-in is a candidate list and has no headline ("40\n43", "Possible offsets:\n0x8\n0x10");
- unicode quotes, apostrophes, dashes, the minus sign and full-width characters become ASCII first (`−40`, `isn’t`, `４０`); any other non-ASCII character is a leftover, and only ASCII digits are numbers;
- `tokens`: the headline must parse **completely** as the accept groups, **each exactly once**, joined by `, ; / and`, a colon or whitespace, a group optionally written twice in a row in two spellings (`0x28 (40)`). The **name groups** (algorithm, direction, base, technique: every group with no number in it) may come in **any order** (`decrypt, XTEA, 32` = `XTEA, decrypt, 32`; `Base64 encode` = `encode, base64`); the **numeric groups keep the order of the question** (bounds lo..hi, the two values of `lcg` or `rotate`), and a number stays where the question puts it relative to the names (`32, XTEA, decrypt` and `XTEA, 32, decrypt` are a leftover; a unit word stays with its number). Numbers are compared by value (`0x08` = `0x8` = `eight`, `16u` = 16, `250,000,000`); number words zero..ninety-nine are numbers, so `40, forty-one` fails like `40, 41`. Around the groups only these may stand, **each tied to the question's own words** (round 4, M1): function words (`the`, `is`, `with`, ...), `answer`/`result`, the question's own unit words (`bytes` for a size, `rounds`/`iterations` for a loop, `states`, `opcodes`, `ns`, `us`, per variant; `bits` is never a unit of a byte count; `64 main`, `64 times`, `64 cycles` are not units, and `main loop` is a phrase only where the question says it), a noun that names the quantity (`offset`, `size`, `value`) **in the lead-in only and only if the question uses that word** (`size 0x8` for an offset question, `key 0x8`, `The size of the key is:\n0x8` are leftovers), a noun that describes a name (`TEA cipher`, `ptrace check`) **directly beside a name group** (`TEA, encrypt, 48, a block cipher` and `decrypt, block 64` are leftovers), `hex`/`hexadecimal` only beside a `0x` number or a bare hex with a letter and `decimal` only beside plain digits (`hex 18` for 0x12 and `decimal 0x6f` are leftovers), `returns`/`return value` only where the question asks what proc returns, directly before the number that is that value (`returns 5` for a state count is a leftover), the task's `allow` phrases ("extended TEA" next to XTEA) and quotes and balanced parentheses. **A number asked in hex** ("(hex, like 0x1c)") is written `0x..` or as a bare hex with a letter: its plain-decimal reading is rejected, because `18` is 0x12 as a decimal and 0x18 to a model that means hex (`0x12 (18)` and `18 (0x12)` are fine; a single digit reads the same in both bases). Digit separators are only the C23 groups (`1'000`, `1_000`, `0xdead'beef`); a run of more than 40 digits is not a number. Everything else is a leftover and rejects: any other word, operator, symbol or number;
- **bounds** (two numeric groups of an interval: the `bounds` family and legacy `threshold`) also take `lo to hi`, `lo..hi`, `lo-hi`, `[lo, hi]`, `from lo to hi`, `lo <= x <= hi`, `lowest lo, highest hi`, a trailing `inclusive`. Nothing exclusive: `>`, `<`, `(lo, hi)`, `[lo, hi)`, `between`, `strictly`, `exclusive`, `greater than` are leftovers, and `lowest 1751, highest 1570` is a label on the wrong bound;
- **context numbers** (`128-bit key`, `(88 bits)`, `8-byte block`, `CRC-32`) are never a hit for a group and are allowed only where the question itself states that quantity (the key width, the block size, the CRC width) or, for a byte count, eight times the value (`RC4, 11 bytes (88 bits)`), **with the label the question gives it**: `128-bit key` and `8-byte block` next to XTEA, `256-bit key` and `64-byte block` next to ChaCha, `16-bit CRC`; `128-bit block`, `32-bit key`, `8-byte key`, `16-bit width` are leftovers. `(64-bit key)` next to XTEA, `(99 bits)` next to an 11-byte key, `AES-40`, `x86-64`, `8-byte aligned` are leftovers;
- `exact_case` (alphabets) and `exact_head` (plaintexts, secrets): the whole headline must be the key, **byte for byte** (round 4, M4). The reply is not normalised: a doubled space, a tab, a no-break space inside the key, a full-width spelling or `\x8f` for `x8f` is another string. Quotes, backticks, markdown, one trailing mark (`. , ; : !`, not `?` or `...`) and a lead-in that **ends in a colon, `=` or one of `is`, `writes`, `reads`, `prints`, `decodes to`**, after function words and nouns of a short list ("The string is", "Alphabet:", "It writes"), are stripped, then nothing but the key may be left. A noun directly in front of the key is a word of the string, not a lead-in (`secret admin status 26`, `path ...`, `output ...`, `in ...` are other strings), and the key must be delimited: `xkey`, `key7`, `/etc/key`, `-key`, `> key`, `KEY`, `key or key2` are other strings. A bare lead-in line ("Answer:", "Here is the string:") is made of function words and the question's own words.

What is stored (`scoring.sft_target`, `rea_bench/targets.py`, `rea_bench/sft.py`) is **never the teacher's text** in a default run (round 4: B2, M4's stored text, m9; a `--reasoning` run stores the reply too, with its own rule: last section). Rounds 2 to 4 each found free prose that carried a wrong fact past the filter in front of it: a sentence that contradicted its headline (`xtea, decrypt, 64` over `It encrypted the data.`), the key's numbers in swapped roles, the family's opposite word in another inflection (`big-endian`, `decoded`, `shifts left`), a plain word for a name. Every one of those filters was a list of bad words or shapes, and the next review found the word that was not on it. So the teacher is a filter only: a task enters the data when the headline of a reply is accepted by `score_strict` (with the agreement rule below), which proves that the task can be answered from the pseudocode, and the assistant message is **rendered from the ground truth**: the canonical headline and one factual justification sentence (`XTEA, decrypt, 16` / `In each of its 16 iterations the loop subtracts the delta 0x9E3779B9 from the running sum.`) from a set of 3-6 phrasings per variant (78 variant/question shapes, legacy included), chosen by `random.Random("truth-template/<task id>/<variant>")`; the headline is one of 4 phrasings chosen by a second seeded RNG (`.../head`), independently of the sentence (round 7, m2: it was `heads[i % 4]` of the sentence index, so the 4th headline of every key was never rendered). A sentence states only SEMANTIC facts (round 5, owner decision, every template of every family): what `proc` computes, returns, accepts or writes as a function of its inputs, and the values of the task's true parameters (a value of the truth, a number or name the question states, or a constant of the variant's template: the TEA delta, the ChaCha rotations, the RC4 state size, a hash's initial value; each a named entry of `facts`). It never describes code structure or compiler output (no "on the stack", "byte by byte", "loop", "comparison", "table lookup", "array", "switch", "divides again and again", "shifts right", no helper that "calls" another), because the compiler decides what the model is shown: gcc builds a stack string straight into the output, clang folds an XOR loop, both rewrite a bound. A specific algorithm is named only where the C is exactly that algorithm (a Python reference in `tests/rea_claims.py` compares them): TEA, XTEA, RC4, ChaCha, Salsa, base64/32/58, FNV-1a, djb2, sdbm; the legacy murmur loop (MurmurHash2's multiplier and seed, one byte at a time, which is not MurmurHash2) is `Murmur-style`, and the scorer still accepts a reply `MurmurHash2` because the question asks which hash it is *based on*. **A sentence may contain only its pattern's literal text and its captured groups** (round 6, M1: the round-5 claims table checked the fact that rendered a sentence and nothing tied the words of the sentence to it, so 66 of 79 false one-edit sentences passed the suite). Every sentence has a PATTERN in `tests/rea_sentences.py`, written independently of `targets.py`: its literal text and a named group wherever it says something that can be wrong (a number, an algorithm, a call, a file, a field, an environment variable, a unit, a byte order, a direction word). The checkers of `tests/rea_claims.py` read the values of the groups FROM THE RENDERED SENTENCE and verify each against the task: its C compiled and run (a Python reference, a sweep of the integer domain, every printable character, every one-edit neighbour of a secret, `offsetof`/`sizeof`, a fake `ptrace`/`getenv`/`fopen`, a clock faked in nanoseconds for either API, a packet model swept over all 256 values of every byte, an fsm proven equal to the compiled machine) or its C source. A sentence that matches no pattern ("wording the table does not know"), a group with a false value and a group that no claim reads each fail: a word that is in no pattern (`union`, `slicing-by-8`) fails, which replaces the round-5 list of structure words. A universal word (any, every, all, always, never, only, each, none, no other, exactly) is allowed only where `tests/test_rea_quantifiers.py` registers the claim and the domain that back it (round-6 B1: "changing any byte makes the checksum fail" was false for Fletcher-16, a byte 0x00 -> 0xFF is not seen). Every sentence of every template is rendered for 200 tasks of every variant at each of two seeds (a training seed and the held-out one, every code form included); `tests/golden/rea_sentences.txt` shows every edit of a template in review; `tests/test_rea_claims_mutations.py` applies the reviewer's 79 false sentences and 13 more to a copy of `targets.py` and requires the table to reject all of them (the golden file is not consulted); a false value in a group (one more iteration, another initial CRC value, a 32-bit width over a reflected 16-bit CRC, the wrong byte order, the name MurmurHash2) fails its checker (`Teeth`); the references the checkers lean on are anchored to the standard library or published vectors (`References`: RC4, ChaCha of RFC 8439, Salsa20, zlib/binascii CRCs, base64/base32, the Bitcoin base58 vectors, Appleby's MurmurHash2). A record is `{messages, task, kind, model, target_source}` with `target_source: "truth-template"` (`"teacher-reasoning"` only in a `--reasoning` run) (round 9, m1: `teacher_headline`, the first accepted raw headline, was a field until round 8 and is gone; `sft.check_records` refuses a record with any other key), and there is no `truncated` or `sentence_dropped` any more. A task gives one record. `python3 -m unittest tests.test_rea_targets` renders 2,000 tasks per family (all eleven) and checks each text against the truth: it scores under both scorers; every fact equals the generator's own `params` (the round count, the offset, the CRC width and form, the endianness, the bounds, the simulated end state of an fsm input; the legacy templates' facts are read back from the C source); every constant is in the C source of that very task; every number and number word in the sentence is a fact, a number of the question, or a counted word the test justifies; no word of the family's vocabulary but the task's own and no opposite of the truth (the other direction, the other endianness, `shifts left` for a reflected CRC) in any inflection; every phrasing of every variant is used. The same check fails on a wrong round count, a wrong delta, `It encrypted the data.`, swapped bounds and a foreign name (`Teeth`), and `python3 tools/rea-bench check` fails a task whose template is missing or renders a text its scorer rejects (the sample stage checks every task before the model download). A task whose chance level is 0.05 or more is kept only when at least 2 of the k samples have an accepted headline; `chance` is the larger of the rate of a guesser that samples the answers and the share of the best constant answer within the variant (TEA/XTEA 0.28-0.31 because the round count 32 is guessed, CRC init and xorout 0.4-0.6, pktsum 0.2-0.5, encoding identification 0.7; the 0.06-0.08 variants `fsm/opcode_value`, `bounds/char_class`, `multi/limit_helper` and the CRC poly variants joined at 0.05 because one lucky sample of six was kept for 31% of their tasks; legacy `skip` has 0.14), so 40 of 62 variants need agreement; that filters one lucky guess, it does not make a 0.5 task hard. The agreement count and the stats are made from replies scored again at the end, so a resumed checkpoint never carries an older scorer's verdict. A failed request (`[error ...]`) is never scored, never stored and counted per family (`errors` in `.stats.json`); more than 5% of them prints a warning, since a dead server makes every later request one, and `--resume` asks the failed tasks and samples again.

### Known limits of the generated data

- **The gate depends on the machine that generated the data.** Which draw a slot keeps depends on the gcc and clang versions that checked it (here gcc 15.2, clang 22.1); the Modal image has the apt compilers of its own base. A fact that fails there becomes an error record (it is not drawn again), so the held-out and training sets can shrink unevenly per family. The Modal-side re-check is the same code (`survive.check`, probes included); the error summary of the decompile stage says how many tasks it cost.
- **A headline that is not exactly the answer is rejected by design** ("Looking at the code...", an answer on line 2, a clause after the answer, a second line that is not a sentence, a number written before the names it belongs behind or two numbers swapped). That is right for data quality and costs yield; the yield of real teacher output has not been measured (no teacher run since this scorer). The measured pass rates are for synthetic realistic phrasings (`tests/rea_attack_matrix.py`: 27 right formats of the review plus family formats; the yield class lists what is given up), not for sampled replies.
- **The gate is a necessary condition, not proof the decompiler shows the value.** It reads `objdump` of the compiled object, not Ghidra pseudocode; a constant a compiler writes as a shift or an lea is not accepted as a probed answer, but the pseudocode may still fold things the instructions show.
- **Small constants** (below 0x20: in every program) are not gated by presence; where a family asks for one (loop counts, return codes, thresholds) the fact carries a probe: the gate puts a marker value in the source at the asked place and requires it in the code. RC4's key length has no probe (it is the size of an array, not a literal) and is only checked by presence of values the gate treats as vacuous: the harness proves the key length, the gate does not prove it is visible.
- **The strobf gate keeps mostly gcc -O0/-O1/-Os and clang -O0/-Os** (round 5, M1). The compiler decodes a constant array at compile time (the string becomes immediates or an XMM constant, no XOR is left), so a draw whose object holds the plaintext is drawn again (`Task.object_gate`, `survive.object_gate_check`: a 4-byte window of the plaintext with at least 3 letters in `.text`/`.rodata*`/`.data*` fails it, the stored bytes must be there; round 6, m6: the clause that accepted a decode constant instead is gone, it decided none of 3,600 objects). Survival of a first draw, seed 99, 100 tasks per variant, `-O0/-O1/-O2/-O3/-Os`, gcc 15.2 and the zig-cc stand-in for clang 22.1: `xor_const` gcc 100/100/0/0/100 and clang 100/0/0/0/74, `sub_const` the same within a point, `xor_rolling` gcc 100/100/28/0/100 and clang 100/0/0/0/67, `alt_xor` gcc 100/100/24/0/100 and clang 100/0/0/0/66, `reverse_xor` gcc 100/100/100/29/100 and clang 100/0/0/0/72, `rot_n` gcc 100/100/100/26/100 and clang 100/65/65/65/74 (percent). Weighted by the generator's own cc/-O mix a first draw survives in 38% (`xor_const`, `sub_const`), 43% (`xor_rolling`, `alt_xor`), 61% (`reverse_xor`) and 80% (`rot_n`) of the cases; no variant is below 20%. The consequence is a data skew like `crc/table_poly`'s: strobf tasks come out at gcc -O0/-O1/-Os and clang -O0/-Os (clang -O1 to -O3 for `rot_n` only), never at gcc -O3 or clang -O2 for most variants, and the model is not trained on the folded forms. The held-out seed needs up to 15 attempts for a slot (mean 4.3, under `HELDOUT_ATTEMPTS = 24`). `stack_string` has no gate: it has no encoded form, its answer is the plaintext as stores or immediates (81% of the objects of the review show it, the rest is unreadable and is filtered by the agreement of the teacher). The local clang is the zig-cc wrapper, whose UBSan source-path string (`.../zig/tmp/<hash>-stdin.c`) holds "cach" and "tmp/"; the gate drops every string that starts with `/` and ends with `.c` before it looks. The Modal side re-checks the gate with its own compilers (`object_gate` is in the task JSON).
- **Legacy `skip` with `b = 0x00` is not trained on** (round 5, M2). The test `p[i] != 0x00` is dead code at every -O level (`proc` is identical with and without it, 60/60 at -O1/-O2/-Os), so nothing in the pseudocode names the skipped byte. The frozen generator still makes those tasks (the pins, `gen` and `check` are unchanged); `families.generate_many` drops them for every seed but the held-out one (about 1 skip task in 7, 1.7% of a legacy run; the decompile stage prints the count), and the held-out seed keeps them, so its bytes are what they were. **Round 7, m1: the rest of `skip` is not trained on either.** The 6 programs with `b != 0x00` are all in the held-out list (the legacy `skip` template draws 7 programs; the list holds all 6 that survive the `b = 0x00` filter), so at a training seed every `skip` draw is dropped by the held-out exclusion, not 1 in 7: `--family legacy --n 600` keeps 0 of its 51 `skip` tasks, `--family all --n 33000` keeps 77 of the 78 templates (`skip` is the one that is absent). The same holds for `keycount`: 7 of its 8 keys are held out, the training data has `port` only (33 of 300 at seed 7). The decompile stage now prints the drop per template (`dropped N of M ... per template (dropped of generated): keycount 267 of 300, skip 249 of 249`) and a warning for a template with nothing left. The behaviour is unchanged on purpose (the legacy generator is frozen, and the held-out list is what keeps evaluation and training disjoint as programs); the SFT data simply has no `skip` task and one `keycount` key, so those two templates are not taught by it and the held-out arm measures them zero-shot.

- **Agreement does not filter a constant guess** (round 5, m8, documented with the review's numbers). A teacher that always answers the most common headline of a variant (`scripts/const_teacher.py` of the review, 500 tasks per variant) is accepted for 0.67-0.73 of every encoding identification variant (`encode, base64`), 0.49-0.51 of the pktsum endianness variants, 0.40-0.57 of CRC init, 0.45 of CRC xorout, 0.43 of `structs/linked_next` and 0.31 of `cipher/xtea_dec`; every variant whose best constant has a share of 0.05 or more carries a `chance` of 0.05 or more and so needs two agreeing samples, which a constant teacher gives. In three variants the share exceeds the carried `chance` by 0.03-0.04 (`base32_encode` 0.718 vs 0.676, `linked_next` 0.434 vs 0.399, `skip` 0.178 vs 0.143): sampling noise at 500 tasks, no decision changes. The stored target is true; this is yield and difficulty, not poison.
- **A task a guess solves often stays easy.** Agreement of two samples removes lucky guesses, not a model that always answers "all ones" (CRC init, xorout). The `chance` of a variant is the share of its best constant answer (round 3, m3), an estimate from 1,000 tasks, so it carries about ±0.02 of noise; a variant just around the threshold of 0.05 (`bounds/index_limit` is 0.037, `fsm/opcode_value` 0.06) can fall either side.
- **The gate's probe is not evidence about the real constant, and an all-ones value passes it blind** (round 3, m4). The marker probe proves that a literal put at the asked place of the source survives into the object, not that the task's own value does; a literal of the task is checked against the generator's own text, so for generator output that part is true by construction. Mutation test, 25 per variant on gated seed-99 tasks, the asked constant changed in the source and the facts kept: the full gate falsely accepts `cipher/rc4` 3/8 and every other variant 0 (ChaCha/Salsa 0/15, TEA/XTEA 0/32, all CRC variants 0/60, antidebug 0/54); with the source-literal check bypassed the marker alone would accept ChaCha 8/8, Salsa 7/7, CRC init 7/9. `forms(0xffffffff)` and `forms(0xffff)` contain 1 (`(-a) & m`), so the plain presence of an all-ones init or xorout is vacuous, and a probe cannot see `x ^ 0xffffffff` compiled to `not eax` (with init changed to a non-all-ones value only 2 of 14 all-ones-xorout tasks keep the literal in the code, the gate still accepts 14/14). The answer is still derivable (`~crc`), so these tasks are not unanswerable, but the gate says "visible" where the pseudocode may show `~x`. RC4's key length has no probe (it is the size of an array).
- **`crc/table_poly` skews towards gcc and away from -O2** (round 3, m6): clang vectorises or folds the table-building loop for most parameters and -O levels, so the gate keeps few clang draws of this variant. Measured at seed 31, n=100: gcc 52% ungated → 85% gated (design 60%), -O2 40% → 14%, -O0 7% → 19%; the other variants and `bounds/char_class`, `structs/init_magic` are back near the design. The held-out seed 1001 keeps draws up to attempt 15 for CRC (9 for bounds, 3 for structs and encoding) and `HELDOUT_ATTEMPTS = 24`: a slot that the Modal compilers redraw past 24 would be a held-out task that no list knows, with a margin of 9 attempts for CRC. Widening it means regenerating the pinned list (`heldout --write`); not done.
- **Held-out is disjoint as a program, for the reserved parameter values**: standard CRC algorithms, ChaCha/Salsa round counts, return codes, packet magics and standard alphabets are split between the held-out seed and training seeds (a held-out seed tests unseen standard algorithms, unseen round counts and shuffled alphabets only). The frozen `legacy` family still repeats programs.
- **The held-out composition differs from training, and some held-out CRC tasks are one constant away from a training task** (round 3, m5). Seed 1001, first 120 per family: `encoding` asks for the 32/58/64-character alphabet in 68% of its tasks (training 32%: only shuffled alphabets are drawn and alphabet asks exist only for custom ones), `crc` is 60% 16-bit (training 44%) and 78% gcc after the gate (training about 60%), `pktsum`, `multi` and `antidebug` values are multiples of 5 only; per-variant counts are balanced, all 1,320 tasks pass the gate and the pinned list. Four of the seven reserved CRC algorithms (`crc32-bzip2`, `crc16-usb`, `crc16-genibus`, `crc16-maxim`) share width, polynomial and direction with a training algorithm and differ in `init` or `xorout`: 42 of the 120 held-out CRC tasks (35%) are one-constant neighbours of a training program. "Disjoint as a program" is literally true; the held-out CRC set tests "algorithms that differ in xorout" as much as "unseen standard algorithms". A held-out score is not comparable family by family with a training-distribution score.

## Next run: the teacher's reasoning, final answer verified (owner decision, 2026-11-11; round 12: several traces per task, quality filters, thinking pilot)

Storing the teacher's text is allowed: the teachers are open-weight models, so the rule "no OpenAI/Anthropic output in the dataset" does not forbid it. Phase A threw it away (only the truth-rendered headline and sentence are stored), which keeps every stored fact right but teaches the answer without the path to it. In distillation work (rejection sampling, STaR, RFT, the DeepSeek-R1 distills) the traces are most of the gain. `--reasoning` keeps them, with the **industry-standard rule** (the owner chose it, 2026-11-11: rejection sampling on the final answer, the reasoning kept as the model wrote it; the references are below the flags):

- **The final answer is verified, the reasoning is kept as it is.** A reply is accepted when the text after its last `Answer:` line passes `score_strict` (the whitelist grammar, not loosened) against the computed truth, plus the agreement rule (2 of the k samples) for the variants with `chance >= 0.05`. The steps in front of it are **not checked, claim by claim or otherwise**: the claims machinery of `tests/rea_claims.py` verifies the truth templates, not free text. **Some steps of an accepted reply may be wrong** (a misread constant, a bad reason that still ends at the right value); the dataset card must say so, and which records are which.
- **One truth record and up to three traces per kept task** (round 12), the same `messages` (system + user): one `target_source: "truth-template"` record (rendered from the truth, as in phase A) and up to `--max-traces` (default 3) `target_source: "teacher-reasoning"` records, each an accepted reply of the teacher, verbatim (`<think>` blocks stripped, whitespace trimmed, nothing else), **distinct** and in sample order (RFT, below). `sft.check_records` accepts exactly the keys `messages, task, kind, model, target_source` with one of those two sources and refuses everything else (round 12 needed no new field). Training can use either or both; the plan stays to **measure** (truth-template only against teacher-reasoning, same tasks, new held-out). **The prompt of a reasoning run is the reasoning one** (`rea_bench.reasoning.SYSTEM_REASONING`: a short step-by-step analysis, then a last `Answer: <value>` line; `SYSTEM_RECIPE` is untouched): the truth-template record of this run is a short answer under a prompt that asks for steps, so for the control arm train on phase A's truth-template data (the original prompt), and do not mix the two sources of one run without meaning to: one prompt, two different targets, is a mixture.
- **Thinking stays off** (`enable_thinking: False`); the steps are the visible answer.

How a reply is read (`rea_bench/reasoning.py`): the last non-empty line must be `Answer: <headline>` (`**Answer:**` is fine, `answer:` and `Final answer:` are not) and only its text is scored. Rejected: no such line, any text after it, an empty one, a `<think>` tag left in the reply, a reply the server cut off at `max_tokens` (the sampler appends `[truncated at max_tokens]`, so a cut that fell right after a correct headline is not an answer), the text of a failed request (never scored, as in phase A). Two `Answer:` lines: the last wins; an `Answer:` in the middle of the steps counts for nothing. Everything the grammar rejects in phase A it rejects here.

| flag (`--stage sample`) | meaning |
|---|---|
| `--reasoning` | the mode above; default off, which is phase A **byte for byte** (a test pins the requests, stats and checkpoint names against the code before this mode, by digest) |
| `--max-traces N` | teacher-reasoning records per kept task (default **3**; at least 1); the truth-template record stays one |
| `--thinking` | a pilot (below): the model reasons first and its reasoning is kept; needs `--reasoning` and an explicit `--max-tokens`; own tag `-reasoning-think` |
| `--max-tokens N` | per reply; default 300 as before, **768 with `--reasoning`**, **no default with `--thinking`** (it must be passed) |
| `--max-len N` | the training window the length rule drops against (default 2048; **required with `--reasoning`**). A record over it is dropped and counted, never cut. `modal_lora.py --max-len N` trains on the same window (default 2048; at 3072 and 4096 the batch is 2 x 8 instead of 4 x 4, same tokens per micro-batch; **not measured on a GPU**) |
| `--quota kind=N,...` | at most N tasks of each listed kind (`structs`, `crc`, ..., or a legacy template such as `xor-key`) and none of another; the first N by id, asked round-robin over the kinds so a run that is stopped early is balanced. Also sizes a non-reasoning run |
| `--budget-usd`, `--gpu-usd-per-h` | the cost line (below): budget 30, L40S 1.95 |

### Several traces per task, and which accepted replies are kept (round 12)

**RFT.** Rejection-sampling fine-tuning (Yuan et al. 2023, "Scaling Relationship on Learning Mathematical Reasoning with Large Language Models", arXiv:2308.01825) samples many reasoning paths per question, keeps the correct ones and fine-tunes on the **distinct** ones: more than one path per question is worth more than one, and the gain comes from the paths being different. RFT dedupes by the equations of a path; there are none to compare here, so the rule is on the text. DeepSeek-R1 (DeepSeek-AI 2025, arXiv:2501.12948) builds its SFT data the same way, several samples per prompt, only the correct ones, and filters out chains of thought with mixed languages (it names that and others and publishes no thresholds); its traces keep their `wait` / `let me recheck` self-corrections, and so do ours. The loop, unreadable and contradiction filters below are the same kind of cleanup and are ours; every threshold is ours and is in `rea_bench/reasoning.py` as a constant.

For each kept task, in the order the replies were sampled, an accepted reply (the last `Answer:` line passes `score_strict`) becomes a trace when it passes **the quality filters, then is not a duplicate of a trace already kept, then fits under the cap**. Each reply that is not stored is counted under exactly one reason, per family, in `.stats.json` (`reasoning.dropped`, `reasoning.by_kind.<family>.dropped`) and in the lines the run prints. The task and its truth record do not depend on any of this: **the agreement rule counts answers**, not the quality of a trace, so a task whose every trace is filtered keeps its truth record (`tasks_without_trace`), and the accepted replies of a task lost to the agreement rule are counted as `in_lost_tasks` (and not examined). `replies = traces + all drops` holds per family.

| reason (in the order tried) | a reply is dropped when | threshold |
|---|---|---|
| `no_think` (thinking run only) | the reply has no reasoning block: the server returned no `reasoning_content` and the text has no `<think>` block | none (a thinking run never stores a record without its reasoning) |
| `mixed_language` | more than a small share of the **letters of the prose** are not ASCII (CJK, Cyrillic, Arabic, accents...). Prose = the text without fenced code, inline code, quoted strings (`"..."`, `'...'`, curly quotes) and without the words the task itself contains (a non-ASCII identifier of its pseudocode or data). Hex dumps (`e4 b8 ad`, `\xe4`), digits, arrows, `x`, `<=`, dashes and curly quotes are not letters or not non-ASCII and never count | **> 0.5%** of the letters (`MIXED_LANGUAGE_MAX`): 3 letters in 600 |
| `repetition` | the same line occurs more than 3 times (lower case, bullets and numbering ignored; at least 12 characters; not a row of numbers), or the same window of 8 words occurs more than 3 times (a window of numbers only is skipped: a table of zeros is not a loop) | **> 3** (`LINE_REPEAT_MAX`, `NGRAM_REPEAT_MAX`, `NGRAM` = 8) |
| `unreadable` | the analysis in front of the `Answer:` line is empty, or every word of it is a word of the answer or a restating word (`the answer is`, `so`, `therefore`, `result`...; `0x20` and `32` are one word): a reply must have some reasoning before its answer. In a thinking run the reasoning block is part of the analysis | no length limit: one line of real reasoning is readable |
| `contradiction` | **only the simple case**: the last explicit statement of a final value in the analysis (`the answer is X`, `final answer: X`, `result = X`, or a conclusion `so / thus / therefore / hence ... is / = / equals X`) names numbers none of which is a number of the task's accept groups (read with the task's own groups: `0x34` and `52` are one value), and no self-correction word (`wait`, `actually`, `hmm`, `let me recheck`, `mistake`, `instead`...) comes after it | unsure means kept: a statement that has a word that is not a value, one right and one wrong number (a hedge), a plain `size is X` or `a / b = c` with no conclusion marker, a name or a string (not looked at: the grammar of the Answer line is their check), a wrong value that was corrected, all stay |
| `duplicate` | the trace is a duplicate of a trace already kept: **normalized text identical** (lower case, whitespace collapsed to one space, think tags removed; digits and punctuation kept) **or token-set Jaccard similarity >= 0.9** (the words of the normalized text, `\w+`, as a set, intersection over union: the same words in another order, or a difference in punctuation only, are one trace). Deterministic, compared with the traces kept so far, in sample order | **>= 0.9** (`JACCARD_DUPLICATE`) |
| `over_cap` | a distinct, clean trace after `--max-traces` were kept | `--max-traces`, 3 |

What this does not do: it does not check the steps (the rule above), it does not detect a contradiction about a name or a string, and a one-word language slip in a long reply is under the 0.5% line. The filters were tried on the cases in `tests/test_rea_traces.py`, not on a model's output: **the share of replies each one drops is not measured** (the pilot measures it). Training on up to three targets for the same prompt is the RFT mixture on purpose; the control (truth-template only) stays one record per task.

### Thinking pilot (`--thinking`, round 12)

For a model that reasons before it answers. The request sets `chat_template_kwargs: {"enable_thinking": true}` (everything else, the system prompt included, is the visible-reasoning run's). The model's reasoning is **kept**: when the server returns `reasoning_content`, or the reply holds `<think>...</think>` (or a `</think>` whose opening tag was in the prompt), the stored text is `<think>\nreasoning\n</think>\n\nvisible reply` (the form the Qwen3.x chat templates render). **Only the visible text's last `Answer:` line is scored**: an `Answer:` line inside the reasoning counts for nothing, whichever way it points. A reply with no reasoning is dropped as `no_think` (the run warns when more than 10% of the accepted replies are), a reply cut off in the reasoning is `truncated`. The quality filters and the duplicate rule apply to the whole trace, reasoning included. The records carry `target_source: "teacher-reasoning"` like the others (no new field), but a thinking run is never mixed with a visible-reasoning one: its tag is `-reasoning-think` (checkpoint `sft-<model>-seed<s>-<family>-reasoning-think.partial.jsonl`, output and `.stats.json`), and `reasoning.mode` in the stats is `"thinking"`.

- `--max-tokens` has **no default** with `--thinking` (the reasoning counts against it; the run stops before anything is rented without it). `--thinking` without `--reasoning` is refused.
- **Cost:** no expected figure. The 5-8x length assumption of the cost line is for visible reasoning and how long this model reasons is not measured; the run prints the worst case (every reply to `--max-tokens`) and warns when that is over `--budget-usd`. Keep `--quota` small first and read `perf` (tokens per second) and the share cut off. The prompt and the reply share one 8,192-token slot of the llama-server (`-c 32768 --parallel 4`): a long prompt leaves less than `--max-tokens` and the reply is cut off. **Not measured.**
- **Not trainable yet:** `modal_lora.py` renders the prompt with `enable_thinking=False`, whose empty think block would sit in front of the record's own; making that right needs the base model's chat template and was not written (it cannot be checked without the tokenizer).

```bash
# a pilot, not run: 20 tasks, 2 samples, one fifth of the worst case. Read the stats before anything bigger.
modal run tools/modal/modal_rea_data.py --stage sample --model codeforge-27b-heretic-q4 --family structs,crc --seed 9 --k 2 --reasoning --thinking --max-tokens 4096 --max-len 8192 --quota structs=10,crc=10
```

### Training on a reasoning file

`modal_lora.py` takes `--config` (the dataset config; default `rea_sft`, phase A's) and `--tag` (the output name). The output directory on the volume and the result files are named by `run_tag`: **`full` (or `smoke`) for the default config with no `--tag`, exactly as before; any other config or tag has a name of its own, and `full` / `smoke` are refused for them**, so a run on a reasoning file can never overwrite phase A's `/out/full`:

```bash
modal run tools/modal/modal_lora.py --config rea_reasoning --max-len 3072                 # -> /out/rea_reasoning, results/phase6/lora/rea_reasoning-train.json
modal run tools/modal/modal_lora.py --config rea_reasoning --tag reasoning-v1 --smoke     # -> /out/reasoning-v1-smoke
```

**Own files.** A reasoning run's checkpoint and output carry `-reasoning` in the tag (`sft-<model>-seed9-<family>-reasoning.partial.jsonl`, `.jsonl`, `.stats.json`): it never writes into, resumes, or moves aside a phase-A checkpoint, and a phase-A output does not block it. The decompiled tasks are still read by the decompile tag, so `--seed` and `--family` are the decompile run's. `--resume` works as before on that checkpoint (a failed request is asked again, nothing else); keep `--max-tokens` the same on a resume: a reply already cut off is rejected, not asked again.

**Length.** The run prints how many teacher-reasoning records fit 2048, 3072 and 4096 tokens (prompt + answer + EOS, the sampler's tokenizer as in round 9) and how many it dropped at `--max-len`; `.stats.json` holds them (`over_length.fits`, `by_source`). A task is lost only when both of its records are over the window, normally the long teacher one goes and the truth record stays. A run also prints how the replies were judged (accepted, answer rejected, no final `Answer:` line, cut off at `max_tokens`, failed) and warns when more than 10% were cut off, and its own throughput (`perf`: tokens per second over the four slots) to correct the assumption below.

**Sizing and cost.** The sampler is one L40S with four requests in flight; the time is the replies. The one measurement is phase A's (owner's figures: CodeForge answered 3,187 tasks x 6 short replies in about 5.5 GPU-hours, `reasoning.PHASE_A_REPLY_S` = 1.04 s per reply; the repo's logs do not record it, nor the tokens per reply). Reasoning replies are 5-8x longer, so tokens dominate, and the projection scales that time by length:

    GPU seconds = tasks x k x 1.04 s x min(max_tokens, factor x 50 tokens) / 50 tokens      (factor 5, 6.5, 8: low, expected, high)
    US$ = GPU hours x 1.95        (L40S, US$0.000542 per second, https://modal.com/pricing; an A100-40GB fallback is US$2.10; CPU and memory add cents)

**Assumptions, all stated in the line the run prints before it rents the GPU:** a phase-A reply is about 50 tokens (headline and one sentence; not recorded), a reasoning reply is 5-8x that (the owner's estimate), and the time scales with the length (an overestimate, since prefill does not scale: the number is a budget guard, not a forecast). The line also gives the worst case, every reply running to `--max-tokens`, and warns when the expected or the high estimate is over `--budget-usd`. The sampler function times out after 5 h, so a run of ~9 GPU-hours takes two calls (`--resume` for the second). The projection counts the tasks of the local `decompiled-<tag>.jsonl` after the quota, else the sum of the quota, else `--n`.

**Recommended run, CodeForge only (`codeforge-27b-heretic-q4`, k=4), about US$20 of the US$30.** Phase-A yields (headline only): pktsum 95%, encoding 92%, crc 83%, structs 80%, antidebug 69%, bounds 46%, fsm 39%, cipher 14%, strobf 7%, multi 2%; the legacy templates 0-100% and are left out (small, frozen). The run takes the five families that were usable but below 85% in full (220 tasks each) and a capped slice of the two high-yield ones (80 each): 1,260 tasks, 5,040 replies, about 850 kept tasks if the phase-A yields hold (220 x 3.17 + 80 x 1.87; not measured for this mode), so about 850 truth-template records and, with up to 3 traces each, at most about 2,500 teacher-reasoning records (fewer: replies that are wrong, filtered or duplicates are not traces, and k=4 samples leave at most 4 candidates per task).

```bash
# 1. decompile (CPU, about US$1.3 for 1,540 tasks): 7 families x 220, n splits evenly
modal run tools/modal/modal_rea_data.py --stage decompile --family structs,crc,antidebug,bounds,fsm,pktsum,encoding --n 1540 --seed 9
# 2. the run: 9.4 GPU-h expected (7.3-11.6), US$18.37 expected (US$14.13-22.61); the second call needs --resume
modal run tools/modal/modal_rea_data.py --stage sample --model codeforge-27b-heretic-q4 --family structs,crc,antidebug,bounds,fsm,pktsum,encoding --seed 9 --k 4 --reasoning --max-len 3072 --quota structs=220,crc=220,antidebug=220,bounds=220,fsm=220,pktsum=80,encoding=80
```

Run a **pilot** first, about US$1.7 expected: the same command with `--quota structs=20,crc=20,antidebug=20,bounds=20,fsm=20,pktsum=8,encoding=8`. It measures the yield of this mode, the share of replies cut off, the tokens per second and what fits 2048/3072/4096, so the cost line can be corrected before the US$18. Its checkpoint is not wasted: the first N tasks of each kind are the same in the big run, so run that one with `--resume --force` (`--force` because the pilot's output file exists) and only the missing replies are asked. If the pilot shows most replies running to the cap (worst case US$43), lower `--quota` or `--k` before the big run. Total: decompile about US$1.3 + sampling US$18.4 = about US$20 expected, US$24 at the high estimate; the pilot's replies are part of the run (resumed), so the pilot costs two container starts, not US$1.7 twice.

**Not measured:** the yield of the reasoning mode, the share each trace filter drops, how many distinct traces a task really has (the recommended k=4 gives at most 4 replies for 3 slots), the tokens per reply, the tokens per second with these prompts, how many records fit each window, the A100 memory at a window above 2048, anything about `--thinking`. The training footgun of round 11 (`modal_lora.py` writing `/out/full` whatever it trained on) is fixed by `--config` / `--tag` above.

The raw replies of phase A are not lost: the checkpoints on the Modal volume (`modal volume get lf-rea-data sft-<model>-seed7-all.partial.jsonl`) hold all six replies per task with their verdict. They are short (headline and one sentence, no reasoning), so they serve the format diagnosis, not this plan.
